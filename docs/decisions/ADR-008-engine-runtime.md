# ADR-008 — Executable engine stages and dedicated Linux toolchain

Status: ACCEPTED for experimental local reference workflows, 2026-10-22. The user explicitly requested runtime integration with actual simulation at each stage and complete toolchain integration. This extends ADR-007; original analysis and general simulation contracts remain unchanged.

Use a dedicated `OpenSoC-Runtime` Ubuntu 24.04 WSL2 distro. Rootfs is downloaded from Canonical and pinned by SHA256 `2a790896740b14d637dbdc583cce1ba081ac53b9e9cdb46dc09a2f73abbd9934`; distro VHD is under workspace `.tools/wsl-runtime`. Only preparation runs as root. Native builds/simulations run as the `opensoc` Linux user. Preserve installed package versions, Python freeze, wheel hashes and offline Python dependency resolution. This is a prepared development environment, not a signed redistributable OS image or universal reproducible/offline installer.

Runtime API owns a separate persisted `runtime-run` kind. `RuntimeRequest` permits only enumerated reviewed profiles and three named scenarios, never arbitrary commands, file paths, uploaded build scripts or vendor generators. Additive `/api/v1/runtime/*` routes do not turn the existing `/api/v1/runs` general simulation endpoint on. Unsupported scenarios are explicitly rejected. The source pins remain the audit baselines: PicoRV32 `ef203c2b0a3fb793280f5114941416c425c5b461`, Ibex `1b29dae8866e6c0f0a3cd9dead53a77b4f45e357`, gem5 `b9da2bfe1e21f6efa2730edd4e80e58c5d965458`.

Each workflow records stages, explicit argv, stdout/stderr, exit codes, checks, worker/source/tool hashes, artifacts and integer simulation times. Firmware compiler and RTL compiler are actual build stages. Ibex uses upstream FuseSoC/Edalize flow; repeated builds may reuse the tool's build cache. A preparation inventory is not a functional verdict. A failed build is FAILED_INFRA, an independent functional oracle failure is COMPLETED_FAIL, cancellation is acknowledged only after worker termination; negative controls are identified by scenario and their oracle, not relabelled as successful hardware behavior.

Worker launches tools in their own process groups with per-process address-space/file/CPU/open-file limits, a per-user inherited process ceiling, wall timeout and log bounds. Cancellation and timeout kill process groups; an executable acceptance check verifies descendants are reaped. Preparation/builds of installed engines have a separate, larger budget. WSL has host filesystem access and outbound networking; it is **not** a full filesystem/network sandbox. Keep arbitrary imported RTL execution disabled. Team RBAC and hostile-code containment remain open.

The Wellen adapter reads actual VCD/FST with a 512 MiB file bound, inventories at most 4096 variables, and returns at most eight signals with 512 transitions each per window. Use integer ticks as strings and explicit `tick_fs`; renderer converts only differences for viewport coordinates. Selection identity is the composite `(run_id, artifact_sha256, signal_id)`. Trace identity is exact; source mapping remains unavailable until a source-to-trace map is proven. Unknown signal IDs fail explicitly. The SVG presents real sampled values and a time cursor; no fabricated port-to-wave mapping or live waveform claim.

Fidelity boundaries: PicoRV32 and Ibex execute actual RTL CPUs; gem5 RISC-V syscall-emulation CPU is an architecture model; standalone SystemC uses a synthetic initiator; SystemC/Verilator reference drives an actual RTL register through a blocking TLM adapter with paired requests/responses. These independent proofs do not constitute gem5 → SystemC → RTL CPU-driven hybrid acceptance. ROHD integration, arbitrary SoC assembly execution and all-vendor support remain separate work.

The initial gem5/SystemC runtime selects the **compiled-in gem5 SystemC kernel** and upstream `Gem5ToTlmBridge64` / `TlmToGem5Bridge64`, with a TimingSimpleCPU workload and memory behind both bridges. It is not the external `util/tlm` libgem5 demo, and it is not the external SystemC 2.3.4 library used by standalone reference workflows. Two real CommMonitors check traffic type/count/order and request/response times. Their correlation is explicitly DERIVED FIFO under the single-outstanding TimingSimpleCPU assumption; packet address/data are unavailable in this decoder. Payload correctness is checked by the executing workload. This advances bridge feasibility without claiming gem5-to-Verilated peripheral integration.
